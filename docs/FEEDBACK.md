# Обратная связь: кнопка в игре → Telegram

Игрок жмёт «✉ написать», пишет пару фраз — отчёт приходит в Telegram владельцу
с уровнем, коробкой, версией сборки и снимком экрана.

## Схема

```
браузер ──POST /api/feedback (JSON)──▶ nginx pozerkalam.space (vdsina, РФ)
                                        ├─ limit_req 6/мин на IP, тело ≤ 1 МБ
                                        └─ proxy_pass 127.0.0.1:8787
                                                       │
                                        pozerkalam-feedback.service (Python 3.11, stdlib)
                                                       ├─ валидация + honeypot + лимит 5/10 мин
                                                       └─ очередь → sendMessage + sendPhoto
                                                              │ HTTPS_PROXY
                                                              ▼
                                                   tinyproxy на боксе 194 (Frankfurt)
                                                              │
                                                              ▼
                                                       api.telegram.org
```

## Почему не напрямую из браузера

Три причины, каждой хватило бы одной:

1. `index.html` отдаётся всем — токен в нём равен токену у всех. Бот
   `@spark_adminfeedback_bot` общий с проектом spark: утечка бьёт по двум проектам
   (чтение чужих сообщений, подмена вебхука, отправка от имени бота).
2. CSP сайта уже это запрещает: `connect-src 'self' https://mc.yandex.ru` — запрос
   на `api.telegram.org` отвалился бы молча, без ошибки в интерфейсе.
3. Прямой вызов нечем ограничить: публичная кнопка «отправить что угодно в мой телеграм».

## Почему через прокси в Франкфурте

**С vdsina нет прямого доступа к api.telegram.org.** Замер соседнего проекта
(`spark/docs/TELEGRAM_BOT.md`, 2026-07-16): напрямую — таймаут 15 с, соединения нет;
через tinyproxy на боксе 194 — HTTP 200 за 0,3 с.

`urllib.request` читает `HTTPS_PROXY` из окружения сам, своего кода для прокси нет.
**`NO_PROXY=api.telegram.org` не ставить ни при каких обстоятельствах** — это ровно та
«оптимизация», которая уводит канал в офлайн.

## Где что лежит

| Что | Где |
|---|---|
| Клиент (форма, кнопки, снимок) | `index.html`, секция `/* ---------- обратная связь ---------- */` |
| Сервис | репозиторий `server/feedback.py` → сервер `/opt/pozerkalam-feedback/feedback.py` |
| systemd | `server/pozerkalam-feedback.service` → `/etc/systemd/system/` |
| nginx location | `server/nginx-feedback.conf` → `/etc/nginx/snippets/pozerkalam-feedback.conf` |
| Зона лимита | `/etc/nginx/conf.d/pozerkalam-limits.conf` (http-контекст) |
| **Секреты** | `/etc/pozerkalam-feedback.env` (600, root) на сервере; локально `.deploy.env` (в `.gitignore`) |

`.deploy.env` — `TG_TOKEN`, `TG_CHAT_ID`, `TG_PROXY`. **У tinyproxy на 194 включён `BasicAuth`**:
адрес без логина и пароля (`http://194.5.65.182:8888`) даёт `407 Proxy Authentication Required`, и
сервис стартует со строкой «telegram НЕДОСТУПЕН» в journal. Правильный вид —
`http://<логин>:<пароль>@194.5.65.182:8888`, учётка берётся из `BasicAuth` в
`/etc/tinyproxy/tinyproxy.conf` на боксе 194. Без первых двух блок деплоя
пропускается с предупреждением, остальной деплой проходит как обычно.

## Контракт эндпоинта

`POST https://pozerkalam.space/api/feedback`, JSON, тело ≤ 1 МБ:

```json
{ "kind":"bug|idea|note", "text":"10…2000 символов", "contact":"≤120, необязательно",
  "hp":"", "shot":"data:image/jpeg;base64,…", "ctx":{"level":"…","build":"…","q":0,"…":"…"} }
```

Ответ `{"ok":true}` или `{"ok":false,"err":"<код>"}`: `bad-json`, `short-text`,
`too-long`, `rate`, `busy`. `{"dry":true}` — валидация без отправки, этим смоук
деплоя проверяет весь путь, не присылая владельцу мусор.

Сервис отвечает **сразу после валидации**, а в Telegram шлёт фоном: путь через
Франкфурт может тянуться секундами, а браузеру важно знать, что отчёт принят.

## Как читать поток

Каждое сообщение начинается с `#позеркалам` и вида отчёта (`#баг`, `#идея`, `#отзыв`) —
по этому тегу отчёты отделяются от потока spark в том же чате. Снимок приходит
вторым сообщением: подпись в Telegram ограничена 1024 символами, и при склейке
длинный текст обрезался бы молча.

## Отчёты перестали приходить

По порядку:

1. `systemctl status pozerkalam-feedback` — сервис жив?
2. `journalctl -u pozerkalam-feedback -n 50` — на старте пишется
   `telegram доступен через прокси …` или `telegram НЕДОСТУПЕН …`.
   **Недоставленные отчёты лежат тут же целиком** — текст игрока не теряется.
3. `journalctl -u tinyproxy` **на боксе 194** — самая частая причина: прокси умер,
   сервис при этом выглядит здоровым.
4. `curl -X POST https://pozerkalam.space/api/feedback -H 'Content-Type: application/json'
   -d '{"kind":"note","text":"проверка канала","dry":true}'` — жив ли путь до сервиса.
5. `getWebhookInfo` у бота — если кто-то поставил вебхук, `getUpdates` перестанет работать
   (на отправку это не влияет).

## Перевыпуск токена

`@BotFather` → `/revoke` → новый токен в `.deploy.env` → `./deploy-pozerkalam.sh`.
Старый перестаёт работать сразу. Делать это обязательно, если токен где-то засветился.

## Анти-спам

Публичный эндпоинт в чужой Telegram — спам-канал по построению. Четыре рубежа:

- nginx `limit_req` 6/мин на IP, `burst=3`, тело ≤ 1 МБ;
- honeypot: скрытое поле `hp`; заполнено — сервер отвечает `{"ok":true}` и молча
  выбрасывает, чтобы отправитель не подбирал обход;
- лимит в памяти сервиса: 5 отчётов с IP за 10 минут;
- кулдаун 60 с в клиенте (`localStorage['trainer_fb_t']`).
