# Сценарии поведения «По зеркалам»

## Зачем

Правило, по которому тренажёр судит игрока, живёт в трёх местах: в голове, в коде детектора
и в проверке инструмента. Сценарий — единственная форма, которую читают все трое: владелец
узнаёт своё требование, код получает проверяемое условие, инструмент — числа, по которым
он падает. Поэтому любая правка правила начинается со сценария, а не с кода.

Второе назначение: сценарии — половина набора, которым мутационный прогон убивает мутантов
(скилл `pozerkalam-mutation`). Сценарий, написанный по правилу, убивает мутанта ровно там,
где ошибка дороже всего.

## Где лежит

`specs/features/<область>/*.feature`; области — `collision`, `clearance`, `city`, `traffic`,
`exam`, `mt`, `render` (вид сцены, только `@ui`). Имя файла — тема, а не номер. Один файл — одна функция, 3–8 сценариев.
Соглашение целиком — `specs/README.md`.

## Два вида сценариев

| Вид | Кто проверяет | Когда выбирать |
|---|---|---|
| `@domain` | `tools/gherkin-run.mjs` — исполняет шаги в живой странице | правило можно проверить без кадров: детектор, зазор, балл, фаза светофора |
| `@ui` | инструмент в браузере; код требования стоит в имени его проверки | правило видно только в движении или на экране: поток за 300 с, клавиши механики, вёрстка |

У каждого сценария ровно один код требования — `@<область>-<тема>-<что>`. **Код неизменяем
после появления**: он стоит в проверке инструмента и в чек-листе, переименуешь — связь
порвётся молча.

## Как гонять

```bash
PW_DIR=/tmp/pw node tools/gherkin-run.mjs          # исполнить @domain (≈4 с)
PW_DIR=/tmp/pw node tools/gherkin-run.mjs traffic  # одна область
node tools/gherkin-check.mjs                       # связь сценарий ↔ проверка
node tools/gherkin-check.mjs --list                # таблица связей
node tools/qa-checklist.mjs                        # пересобрать docs/qa-checklist.md
```

Гейт падает на: сценарии без кода, без тега вида или области, без блока `Ссылка:`;
`@ui`-сценарии без проверки; коде в проверке без сценария; устаревшем чек-листе.

## Порядок работы

1. Правило меняется — сначала сценарий, потом код. `@domain`-сценарий обязан покраснеть до
   правки и позеленеть после.
2. Новый шаг добавляется в `tools/steps/domain.js` только под новое понятие: **сначала ищем
   существующий шаг**, чаще всего подходит он.
3. `gherkin-run` и `gherkin-check` — зелёные, чек-лист пересобран в том же коммите.

## Частые ошибки

- **Сценарий описывает реализацию.** «Тогда `trafficGap` возвращает 99» — плохо;
  «Тогда путь свободен» — хорошо. Сценарий обязан пережить рефакторинг.
- **Числа списаны с текущего вывода.** Такой сценарий проходит всегда и не убивает ни
  одного мутанта. Числа берутся из правила, из регламента или из замера.
- **Один сценарий на пять проверок.** По красному сценарию должно быть понятно, что
  сломалось; каждое «Тогда» — про своё.
- **Адрес без уточнения.** «светофор группы NS» — это четыре разных светофора со своими
  смещениями; адрес обязан быть однозначным, иначе сценарий зелёный по случайности.
- **Чек-лист правят руками.** Он перезаписывается генератором; правится сценарий.
