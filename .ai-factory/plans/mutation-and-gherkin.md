## Чем этот проект отличается от load-calculator

Систему нельзя перенести файлами — у неё нет ни одной точки опоры в этом репозитории.

| В load-calculator | Здесь | Что делаем |
|---|---|---|
| pytest-bdd исполняет `.feature` | тест-раннера нет вообще | свой раннер `@domain`-сценариев в странице |
| vitest-тесты, код требования в `it(...)` | самописные инструменты, код требования пойдёт в `check(...)` | тот же гейт связи, другой парсер |
| Stryker мутирует `src/**/*.ts` | один `index.html` с инлайновым `<script>` | текстовый мутатор по скрипту + сборка мутанта во временный файл |
| mutmut мутирует python-формулы | формулы живут в том же скрипте | одна зона мутаций на весь проект |
| `pnpm`/`uv` ставят зависимости | zero-dependency, `package.json` нет и не будет | только stdlib Node + `playwright-core` из `PW_DIR` |
| прогон тестов — секунды | `level-audit` — 4 минуты | нужен отдельный быстрый набор: цель < 5 с |

Два следствия, которые определяют весь план:

1. **Мутанту нужен быстрый набор.** Прогонять `level-audit` на каждом мутанте нельзя: 300 мутантов × 4 мин = сутки. Поэтому сначала появляется `tools/unit-check.mjs` (утверждения по чистым функциям, один прогон страницы) и исполняемые `@domain`-сценарии — вместе они и есть «тесты» для мутационного прогона.
2. **Сценарий должен быть исполняемым, а не только документом.** В load-calculator `@ui`-сценарии документарные, потому что их закрывают vitest-тесты. Здесь UI-проверок мало, а правила (кто кому уступает, что считается касанием, сколько баллов стоит ошибка) — это и есть домен. Значит `@domain` здесь больше, чем там, и он исполняется.

### Фаза 1 — Gherkin

#### T1. Каркас сценариев
**Файлы:** `specs/features/<область>/*.feature` (новые), `.gitattributes` при необходимости
- Каталоги по областям: `collision/`, `clearance/`, `city/`, `traffic/`, `exam/`, `mt/`, `coach/`.
- Обязательные части файла: `# language: ru`, `Функция:`, краткое описание, блок `Ссылка:` (замечание владельца, пункт регламента, СП/ПДД, коммит, номер задачи Vikunja).
- Теги трёх видов: **вид** (`@domain` — исполняется, `@ui` — связан с `check(...)`), **область** (`@collision`, `@traffic`, …), **код требования** (`@<область>-<тема>-<что>`, например `@traffic-yield-window`). Код неизменяем после появления: он стоит в проверке и в чек-листе.
- Числа в шагах берутся из регламента, из замера или из правила, а не из текущего вывода кода. Сценарий, списанный с реализации, проходит всегда.
- **Логи:** нет (только текстовые файлы).

#### T2. Гейт связи сценарий ↔ проверка
**Файл:** `tools/gherkin-check.mjs` (новый)
- Парсит `specs/features/**/*.feature` (свой минимальный парсер: теги, `Сценарий:`, `Структура сценария:`), собирает коды требований.
- `@ui` — код обязан встречаться в тексте `tools/*.mjs`/`tools/*.js` (в имени `check('… (@код)')` или в комментарии рядом).
- `@domain` — код обязан иметь сценарий, который умеет исполнить `gherkin-run` (все шаги есть в словаре).
- Проверка в обе стороны: сценарий без проверки — падение; `check(...)` с кодом, которого нет ни в одном сценарии — падение (код переименовали, связь порвалась молча).
- Сценарий без кода требования — падение.
- `--list` печатает таблицу «код · вид · файл:строка · что его проверяет».
- Выход 1 при любом разрыве связи.
- **Логи:** построчный вывод по каждому сценарию при `--list`, сводка «N сценариев, M без проверки» всегда.

#### T3. Исполняемые `@domain`-сценарии
**Файлы:** `tools/gherkin-run.mjs`, `tools/steps/*.mjs` (новые)
- Раннер поднимает страницу один раз (playwright-core из `PW_DIR`, как `demo-vio`), дальше каждый сценарий исполняется внутри страницы: загрузка уровня, установка позы `setBody`, вызовы `violationsTick`/`clearances`/`trafficGap`/`examPenalty`, чтение `#coach`.
- Словарь шагов — обычные функции с регулярным выражением, по образцу pytest-bdd: `Дано уровень «30 · Круговое движение»`, `Когда машина стоит в (61.5, −4.95) курсом 90°`, `Тогда нарушений нет`, `Тогда начислено 5 баллов по коду «yield»`.
- **Сначала ищем существующий шаг**, новый добавляем только под новое понятие.
- Область видимости: шаги не лезут в приватные функции мимо публичного поведения — сценарий обязан пережить рефакторинг.
- Выход 1 при первом упавшем сценарии, с печатью шага и ожидания.
- **Логи:** `✓`/`✗` на сценарий, при падении — шаг, ожидание, фактическое значение, поза машины.

#### T4. Сценарии задним числом
**Файлы:** `specs/features/**` (новые), `tools/*.mjs` (правка имён `check(...)`)
Пять областей, по 4–8 сценариев на файл:
- **Детекторы** (`@domain`): красный/жёлтый, стоп-линия и её защёлка `_seen`, сплошная, встречка по направлению, перестроение без поворотника, разворот с путей, непропуск по моменту сближения, кулдаун зоны на пару «зона × машина».
- **Габариты и касание** (`@domain`): касание считается по оболочке кузова, а не по прямоугольнику (цифры из `hull-check`: 1,7 см при 6°, 9,2 см при 35°); бордюр не валит попытку; касание защёлкивается один раз.
- **Поток** (`@domain`): машина потока не выезжает на встречную, стоит на красный, держит дистанцию, уступает по правилу «приедет позже», окно считается в точке в 6 м перед носом.
- **Экзамен** (`@domain`): 5/3/1 балла, провал на сумме 7, аварийные валят сразу, тренировочный режим разбирает вместо провала, три маршрута проходимы.
- **МКПП и экран** (`@ui`): передача только со сцеплением, «заглох» на брошенном сцеплении, `#tstart` занимает место ручника, тач-полоса не перекрывается — коды проставляются в существующие `check(...)` в `tools/mt-check.mjs` и `tools/mirror-check.mjs`.
- **Логи:** нет (правка имён проверок не меняет их поведение).

#### T5. Чек-лист для ручной проверки
**Файлы:** `tools/qa-checklist.mjs`, `docs/qa-checklist.md` (новые)
- Собирается из тех же сценариев, руками не правится: область → сценарий → шаги → ожидаемые числа.
- У каждого сценария стоит «авто» (исполняется раннером) или «руками» (`@ui`).
- Ключи `--area`, `--only ui|domain`, `--out`.
- Пересобирается в том же коммите, что и правка сценариев; `gherkin-check` падает, если чек-лист устарел (сверка по хэшу списка кодов).
- **Логи:** «собрано N сценариев в M областях».

**Коммит-чекпоинт 1:** `test(specs): Gherkin-сценарии и гейт связи с проверками` (T1–T5)

#### T8. Прогон и гейт
**Файлы:** `tools/mutation.mjs`, `reports/mutation.md` (новые)

- **Логи:** на каждый мутант — номер, функция, строка, правка, вердикт и кто убил (`unit-check` или код сценария).

## Риски и на что смотреть

| Риск | Признак | Что делать |
|---|---|---|
| Быстрый набор медленный | прогон мутанта дольше 5 с | убрать из `unit-check` всё, что рендерит или ждёт кадров |
| Мутант ломает загрузку страницы | «выжил» на самом деле = страница упала | считать падение страницы убийством, но печатать отдельным статусом |
| Сценарии списаны с реализации | мутационный балл высокий, а дефекты проходят | числа в шагах — из правила и из замера, не из вывода кода |
| Эквивалентных мутантов много в одной функции | балл не растёт | это сигнал, что функция переусложнена, а не что нужен новый тест |
| Гейт связи мешает работать | правки рвут связь молча | код требования неизменяем; `gherkin-check --list` показывает связь |

## Не входит в скоуп

- Мутации обучающего слоя (`phaseTick`, `goalMiss`, `coachGoalTick`) и рендера.
- CI: прогон остаётся локальным (в репозитории нет CI-конфигурации для тестов).
- Замена существующих инструментов — они остаются, гейты добавляются рядом.
